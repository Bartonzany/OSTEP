# 25 - 常见并发问题

并发 bug 大致分两类：**非死锁 bug**（占 70% 以上）和**死锁 bug**。非死锁 bug 的根源就两个——复合操作没原子化（原子性违反）、有依赖的顺序没强制（顺序违反）；死锁得同时满足四个条件，最实用的解法是预防，尤其是给锁定个固定顺序。

## 一、非死锁 bug

Lu 等人统计了 MySQL、Apache、Mozilla、OpenOffice 的 105 个并发 bug，其中 74 个是非死锁 bug（占 70% 以上）；非死锁里又几乎全是下面两类（占 97%）。

### 1. 原子性违反

一段本该原子执行的"多步内存访问"，因为没上锁被调度打断，结果就不对了。典型如 MySQL 的真实 bug——线程 1 先检查 `proc_info` 非空再打印，线程 2 却在中间把它置 NULL：

```c
// 线程1：检查 proc_info 非空后打印
if (thd->proc_info) {
    fputs(thd->proc_info, ...); // 可能 dereference NULL
}

// 线程2：将 proc_info 设为 NULL
thd->proc_info = NULL;
```

问题在于"检查 → 使用"这两步之间被线程 2 插进来，`proc_info` 变 NULL，线程 1 就崩了。本质是"检查 + 使用"这个复合操作没保证原子。

修法很简单：给共享数据的访问加锁，把复合操作包成原子。

```c
pthread_mutex_t proc_info_lock = PTHREAD_MUTEX_INITIALIZER;

// 线程1
pthread_mutex_lock(&proc_info_lock);
if (thd->proc_info) {
    fputs(thd->proc_info, ...);
}
pthread_mutex_unlock(&proc_info_lock);

// 线程2
pthread_mutex_lock(&proc_info_lock);
thd->proc_info = NULL;
pthread_mutex_unlock(&proc_info_lock);
```

### 2. 顺序违反

两个内存访问的先后顺序没被强制，结果后面的操作在前面的操作完成前就执行了。典型是"先初始化、后访问"的依赖：线程 1 创建 `mThread`，线程 2 直接读它，若线程 2 跑在初始化之前就空指针。

```c
// 线程1：初始化 mThread
void init() {
    mThread = PR_CreateThread(mMain, ...); // A：创建线程
}

// 线程2：直接访问 mThread
void mMain(...) {
    mState = mThread->State; // B：依赖 A 完成，可能访问 NULL
}
```

本质是没强制"初始化（A）→ 访问（B）"的顺序。修法是用条件变量 + 锁：初始化方做完后置标志再 `signal`，访问方循环等标志。

```c
pthread_mutex_t mtLock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t mtCond = PTHREAD_COND_INITIALIZER;
int mtInit = 0; // 状态标记：0=未初始化，1=已初始化

// 线程1（初始化）
void init() {
    mThread = PR_CreateThread(mMain, ...);
    pthread_mutex_lock(&mtLock);
    mtInit = 1; // 标记初始化完成
    pthread_cond_signal(&mtCond); // 唤醒等待线程
    pthread_mutex_unlock(&mtLock);
}

// 线程2（访问）
void mMain(...) {
    pthread_mutex_lock(&mtLock);
    while (mtInit == 0) { // 循环等待（防虚假唤醒）
        pthread_cond_wait(&mtCond, &mtLock);
    }
    pthread_mutex_unlock(&mtLock);
    mState = mThread->State; // 安全访问
}
```

这两类 bug 的规律：要么"复合操作没原子化"，要么"依赖顺序没强制"。修复原则——原子性问题用锁或原子指令，顺序问题用条件变量或信号量。它们触发又依赖线程调度、极难复现，最好靠代码审查提前规避，而不是等测试崩了再去查。

## 二、死锁

多个线程各自持有对方想要的资源又不放手，全都永久阻塞。

死锁要同时满足四个条件，缺一个就不会发生：

1. **互斥**：资源（锁）只能被一个线程独占；
2. **持有并等待**：线程握着部分资源，又等别的资源；
3. **不可抢占**：资源不能被强行从持有者手里夺走；
4. **循环等待**：存在一环线程，每个都在等下一个手里的资源。

最典型的双锁循环：

```c
// 线程1：先拿 L1，再拿 L2
pthread_mutex_lock(L1);
pthread_mutex_lock(L2); // 若 L2 被线程2持有，阻塞

// 线程2：先拿 L2，再拿 L1
pthread_mutex_lock(L2);
pthread_mutex_lock(L1); // 若 L1 被线程1持有，阻塞
```

线程 1 拿到 L1 后被切走、线程 2 拿到 L2，之后就互相等着，死锁。

死锁为什么难防：一是大型系统组件依赖嵌套（虚拟内存系统要访问文件系统、文件系统又要访问内存）；二是封装把锁的获取顺序藏起来了（比如 Java Vector 的 `AddAll()` 内部一次拿两个 Vector 的锁，调用方根本不知道）。

### 解法：预防 > 避免 > 检测恢复

#### 预防（最实用）

思路是破坏四个条件之一，首选破坏"循环等待"。

**1. 锁排序（破坏循环等待）**

所有线程按固定的全局顺序拿锁。简单场景约定"L1 先于 L2"、或"小 ID 锁先于大 ID 锁"；通用的做法是按锁的内存地址排序，适用于参数顺序不确定的情况：

```c
void do_something(pthread_mutex_t *m1, pthread_mutex_t *m2) {
    if (m1 > m2) { // 按地址高低排序
        pthread_mutex_lock(m1);
        pthread_mutex_lock(m2);
    } else {
        pthread_mutex_lock(m2);
        pthread_mutex_lock(m1);
    }
    // 临界区
    pthread_mutex_unlock(m1);
    pthread_mutex_unlock(m2);
}
```

比如 Linux 内核内存映射代码里，就明文规定了 10 组锁的获取顺序（如 `i_mutex` 先于 `i_mmap_rwsem`）。

**2. 原子获取所有锁（破坏持有并等待）**

加一把全局锁，先把要用的锁一次全拿齐再放全局锁，不出现"握着一部分等另一部分"：

```c
pthread_mutex_t global_lock; // 全局锁保护锁获取过程
pthread_mutex_lock(&global_lock);
pthread_mutex_lock(L1); // 原子获取所有需要的锁
pthread_mutex_lock(L2);
pthread_mutex_unlock(&global_lock);
```

缺点是破坏封装（得提前知道要哪些锁）、降低并发（锁握太久）。

**3. trylock 退避（破坏不可抢占）**

用 `pthread_mutex_trylock()` 尝试拿锁，拿不到就释放已持有的、退回去重试：

```c
top:
pthread_mutex_lock(L1);
if (pthread_mutex_trylock(L2) != 0) { // 尝试获取 L2，失败则退避
    pthread_mutex_unlock(L1);
    usleep(rand() % 100); // 随机延迟防活锁
    goto top;
}
// 临界区
pthread_mutex_unlock(L2);
pthread_mutex_unlock(L1);
```

注意：可能引发活锁（反复退避重试、毫无进展），所以要加随机延迟错开。

**4. 无锁结构（破坏互斥）**

用 CAS、LL/SC 这类硬件原子指令直接构建数据结构，干脆不用锁：

```c
void AtomicIncrement(int *value, int amount) {
    do {
        int old = *value;
    } while (CompareAndSwap(value, old, old + amount) == 0);
}
```

缺点是实现复杂（要处理重试、ABA 问题），只适合简单数据结构。

#### 避免（适用场景有限）

基于全局资源需求来调度，从源头避免死锁，比如 Dijkstra 的银行家算法：已知 T1、T2 都要 L1 和 L2，就让它们在一个 CPU 上串行跑。缺点是要提前知道所有线程要哪些锁，限制并发，通用系统用不上。

#### 检测与恢复（兜底）

允许死锁偶尔发生，定期检测（构建资源依赖图、找环），发现了再恢复：简单的重启程序（死锁罕见的系统）、复杂的（数据库里）终止一个线程释放资源并修复一致性。适合死锁概率低、恢复成本低的场景。

## 三、几条设计提示

- **Tom West 定律**："不是所有值得做的事都值得做好。"如果死锁一年才一次、重启成本又低，别投入大力气做完美预防，先保证代码简洁。
- **非死锁 bug 优先规避**：复合操作（检查后修改、读取后使用）必须加锁；线程间有依赖时用条件变量/信号量强制顺序，别"先访问后初始化"。
- **锁的使用习惯**：最小持有时间，锁只包临界区、不跨 I/O/睡眠；大型项目里把锁顺序文档化，别让同事误用。

## 四、总结

1. 并发 bug 的根源：非死锁 bug 缺原子性/顺序控制，死锁 bug 缺锁顺序约定；
2. 非死锁修复：原子性用锁/原子指令，顺序用条件变量；
3. 死锁修复：优先"锁排序"预防，简单高效，覆盖大多数场景；
4. 无锁结构能彻底绕开死锁，但实现复杂，只在性能敏感处用；
5. 并发 bug 难复现，要靠代码审查（查原子性、查锁顺序）提前规避，不能只靠测试。

## 五、作业方向（Code）

代码在 `OSTEP/homework/threads-bugs/`，是同一个"向量相加" `vector_add()` 的五种实现，`make` 后直接跑。对比它们怎么处理锁：

1. `vector-deadlock.c`：固定 dst→src 顺序拿锁，观察死锁触发条件、线程数/循环次数对死锁概率的影响；
2. `vector-global-order.c`：按地址给锁定全局顺序，理解为什么能避免死锁；
3. `vector-try-wait.c`：`trylock` 退避实现，和 `vector-global-order.c` 比性能；
4. `vector-avoid-hold-and-wait.c`：全局锁一次性取锁（对应"破坏持有并等待"）；
5. `vector-nolock.c`：无锁实现（原子 fetch-and-add），验证语义和有锁版有何不同、性能优势。

### 实验结果

`make` 编译后运行。注意：`vector-nolock.c` 原内联汇编在 64 位 gcc 下编不过，改用等价的 `__sync_fetch_and_add` 后才通过。

**1. vector-deadlock：-d 触发死锁**

`-d` 让奇数号线程调 `add(1,0)`、偶数号调 `add(0,1)`，两个线程按相反顺序拿两把锁，循环次数一多就撞上循环等待、挂死：

```shell
timeout 3 ./vector-deadlock -d -l 100000 -n 2
```

```text
退出码 124（超时未结束 = 死锁）
```

**2. vector-global-order：锁排序，不死锁**

同样 `-d` 两线程，但按地址高低给锁定了全局序，永远先拿地址小的那把，不会循环等待：

```shell
timeout 3 ./vector-global-order -d -l 100000 -n 2
```

```text
退出码 0（正常结束）
```

**3. vector-try-wait：trylock 退避**

拿不到第二把锁就释放已持有的、退回重试，所以不死锁，但会反复空转重试：

```shell
./vector-try-wait -d -l 10000 -n 2
```

```text
Retries: 172065
```

**4. vector-avoid-hold-and-wait：全局锁一次取锁**

```shell
timeout 3 ./vector-avoid-hold-and-wait -d -l 100000 -n 2
```

```text
退出码 0（正常结束）
```

**5. vector-nolock：无锁 fetch-and-add**

```shell
timeout 3 ./vector-nolock -d -l 100000 -n 2
```

```text
退出码 0（正常结束）
```

**性能对比：锁排序 vs trylock 退避**

同样 `-d -l 10000 -n 2 -t`，锁排序 0.01s、trylock 退避 0.03s，后者还重试了 85504 次——重试空转比直接阻塞更费：

```shell

./vector-try-wait -d -l 10000 -n 2 -t
```
