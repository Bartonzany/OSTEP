# 23 - 条件变量

条件变量（Condition Variable）解决的是"线程要等某个条件成立才能继续"的问题：条件不满足时，线程不空转烧 CPU，而是把自己放进一个队列睡觉（`wait`），等别的线程改了条件再唤醒它（`signal`/`broadcast`）。它本质是个显式队列，本身不存状态，必须和锁 + 一个状态变量搭配使用。

## 一、POSIX接口

```c
pthread_cond_t cond;                               // 声明条件变量
pthread_cond_t cond = PTHREAD_COND_INITIALIZER;    // 初始化（静态） 

pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);   // 等待：必须持有锁，原子释放锁并休眠，唤醒后重新获取锁
pthread_cond_signal(pthread_cond_t *cond);                         // 唤醒：唤醒一个等待该条件的线程
pthread_cond_broadcast(pthread_cond_t *cond);                      // 广播：唤醒所有等待该条件的线程
```

几个必须记住的点：

1. `wait` 调用前必须持有锁，否则行为未定义；
2. `wait` 会**原子地**完成"释放锁 + 休眠"（两步并一步，防止"检查条件"和"睡觉"之间被别的线程插队）；
3. 线程从 `wait` 返回前会重新拿到锁；
4. 条件变量不保存任何状态，条件由外部变量（`done`、`count`）表达。

## 二、入门例子：线程 join

父线程等子线程结束，用 `done` 表示"子线程跑完了"。

**方案 1（自旋等待，错）**：

```c
volatile int done = 0;
void *child(void *arg) { done = 1; return NULL; }
int main() {
    pthread_create(&c, NULL, child, NULL);
    while (done == 0); // 自旋浪费CPU
    return 0;
}
```

问题：白烧 CPU——单 CPU 上子线程可能拿不到 CPU，父线程就无限自旋；多 CPU 上也浪费资源。

**方案 2（只条件变量、无状态变量，错）**：

```c
pthread_cond_t c;
pthread_mutex_t m;
void thr_exit() { Pthread_cond_signal(&c); } // 无状态标记
void thr_join() { Pthread_cond_wait(&c, &m); }
```

问题：若子线程先执行并 `signal`，父线程之后才 `wait`，信号就丢了，父线程永久睡下去。

**方案 3（正确：状态变量 + 锁 + 条件变量）**：

```c
int done = 0;
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  c = PTHREAD_COND_INITIALIZER;

void thr_exit() {
    Pthread_mutex_lock(&m);
    done = 1;                    // 先改状态
    Pthread_cond_signal(&c);     // 再唤醒
    Pthread_mutex_unlock(&m);
}
void thr_join() {
    Pthread_mutex_lock(&m);
    while (done == 0)            // 循环检查，不满足才睡
        Pthread_cond_wait(&c, &m);
    Pthread_mutex_unlock(&m);
}
```

对照方案 3 的正确代码，这三件事缺一不可：

1. **用状态变量 `done` 记录条件**：条件变量自己不保存任何状态，必须有一个变量来表达"子线程到底跑完没有"。没有它（方案 2），子线程先 `signal`、父线程才 `wait`，这次唤醒就丢了，父线程永久睡下去。
2. **用 `while` 循环检查，而不是 `if`**：线程被唤醒后，条件可能已经被别的线程改掉（或者根本是虚假唤醒），所以醒来后必须重新查一次 `done`，不满足就继续睡。
3. **改状态和 `signal` 都放进锁里**：`done = 1` 和 `signal` 这两步要保持原子，别让别的线程插在中间，否则会出现"改了状态但还没发信号"的窗口，导致等待的一方错过唤醒。

## 三、生产者/消费者（有界缓冲区）

- 生产者线程：生成数据并放入缓冲区；
- 消费者线程：从缓冲区取出数据并消费；
- 约束：缓冲区满时生产者不能放，空时消费者不能取，用 `count` 表示当前数据量。

### 1. 单条件变量 + `if`：错

```c
pthread_cond_t cond;
pthread_mutex_t mutex;
int count = 0; // 缓冲区数据量（0=空，1=满）

void *producer(void *arg) {
    Pthread_mutex_lock(&mutex);
    if (count == 1) Pthread_cond_wait(&cond, &mutex); // if 判断
    put(i); count = 1;
    Pthread_cond_signal(&cond);
    Pthread_mutex_unlock(&mutex);
}

void *consumer(void *arg) {
    Pthread_mutex_lock(&mutex);
    if (count == 0) Pthread_cond_wait(&cond, &mutex); // if 判断
    get(); count = 0;
    Pthread_cond_signal(&cond);
    Pthread_mutex_unlock(&mutex);
}
```

多消费者时出问题：生产者唤醒一个消费者，结果另一个消费者抢先消费掉数据，被唤醒的那个醒来后无数据可取。`if` 只在睡之前查一次条件，没管"醒来后条件已变"。

### 2. 单条件变量 + `while`：还是错

```c
// 仅把 if 换成 while，其余同方案 1
while (count == 1) Pthread_cond_wait(&cond, &mutex); // 生产者
while (count == 0) Pthread_cond_wait(&cond, &mutex); // 消费者
```

单消费者场景能修好"醒来没数据"，但多生产者/多消费者下，`signal` 可能叫醒**错误类型**的线程：消费者消费后 `signal` 唤醒的是另一个消费者（而不是该被叫醒的生产者），最终大家都睡着——死锁。

### 3. 双条件变量 + `while`：对

用两个条件变量分开两种"等待"：`empty`（生产者等缓冲区有空位）、`fill`（消费者等缓冲区有数据）。生产者等 `empty`、唤醒 `fill`；消费者等 `fill`、唤醒 `empty`。这样 `signal` 只会叫醒正确的那一类线程，再配合 `while` 应对醒后条件变化：

```c
pthread_cond_t empty, fill;
pthread_mutex_t m;
int count = 0;
#define MAX 10

void *producer(void *arg) {
    Pthread_mutex_lock(&m);
    while (count == MAX) Pthread_cond_wait(&empty, &m);  // 满了，等空位
    put(); count++;
    Pthread_cond_signal(&fill);                          // 通知有数据
    Pthread_mutex_unlock(&m);
}
void *consumer(void *arg) {
    Pthread_mutex_lock(&m);
    while (count == 0) Pthread_cond_wait(&fill, &m);     // 空了，等数据
    get(); count--;
    Pthread_cond_signal(&empty);                         // 通知有空位
    Pthread_mutex_unlock(&m);
}
```

生产者的 `signal(fill)` 只会叫醒消费者、消费者的 `signal(empty)` 只会叫醒生产者，所以不存在"叫错类型"的问题。跟踪一遍（2 个消费者 + 1 个生产者，缓冲区 MAX=1）：

对比上一节那种死锁表：同样卡在 `c5` 这一格，这次消费者 `signal(empty)` 叫醒的是**生产者**（正确类型），而不是另一个消费者；生产者被唤醒后继续生产、再叫醒下一个消费者，链条转起来，不再卡死。

### 4. 多槽循环缓冲

把单槽扩成环：`buffer[MAX]` + 写指针 `fill_ptr` + 读指针 `use_ptr` + 数量 `count`，`put`/`get` 各自取模自增。槽位多了，生产者/消费者被唤醒的频率降低，上下文切换开销跟着降，提升并发效率。

```c
int buffer[MAX];
int fill_ptr = 0; // 写入指针
int use_ptr = 0;  // 读取指针
int count = 0;    // 数据个数

void put(int value) {
    buffer[fill_ptr] = value;
    fill_ptr = (fill_ptr + 1) % MAX; // 循环写入
    count++;
}

int get() {
    int tmp = buffer[use_ptr];
    use_ptr = (use_ptr + 1) % MAX; // 循环读取
    count--;
    return tmp;
}
```

和单槽（MAX=1）相比，多槽的关键好处是"不用每放一个就等对方、每取一个就等对方"。下面以 MAX=2、1 生产者 + 1 消费者为例跟踪（`[--]` 表示空、`[#-]` 一个、`[##]` 满）：

| :---: | :---: | :---: | :---: | :---: | :---: | :--- |
| **p1** | 运行 | | 就绪 | 0 | [--] | 生产者拿锁 |
| **p2** | 运行 | | 就绪 | 0 | [--] | 没满，不用等 |
| **p4** | 运行 | | 就绪 | 1 | [#-] | 放入第 1 个 |

对比单槽：MAX=1 时生产者放一个就得等消费者取走（反过来也一样），来回 ping-pong、每次都要 `wait` + `signal` 一次；MAX=2 时生产者和消费者都能**连做两个**才阻塞，唤醒次数减半。槽越多，阻塞互换的越少。

## 四、覆盖条件（Covering Conditions）

当等同一把条件的线程"条件不同"（比如 A 要 100 字节内存、B 只要 10 字节），`signal` 可能叫醒仍不满足的 A，而满足条件的 B 却还在睡。这时改用 `broadcast` 把所有等待者都叫醒，每个线程 `while` 重新查自己的条件、满足的留下干活、不满足的继续睡：

```c
void free(void *ptr, int size) {
    Pthread_mutex_lock(&m);
    bytesLeft += size;
    Pthread_cond_broadcast(&c); // 唤醒所有等待线程
    Pthread_mutex_unlock(&m);
}
```

所有等待线程被唤醒后各自重新检查 `while (bytesLeft < size)`，满足的继续执行、不满足的再睡回去。多叫醒几个线程有轻微开销，但保证正确，适合内存分配这类"各线程条件不一"的场景。

## 五、使用规则

- **锁与原子性**：`wait` 调用时必须持有锁，否则在"检查条件"和"进入睡眠"之间可能发生中断，导致条件已被修改却错过信号；`signal`/`broadcast` 同样建议在持锁状态下调用，保证修改条件与发送信号是原子操作。
- **`while` 而非 `if`**：主流系统的 Mesa 语义下，线程被唤醒后条件可能已改变（被其他线程抢先修改），且线程库存在虚假唤醒（无信号也可能被唤醒），因此必须重新检查条件，不满足则继续等待。
- **`signal` 与 `broadcast` 的选择**：`signal` 唤醒单个线程，开销更低，适用于"条件满足后只有一个线程能继续"的场景（如生产者/消费者）；`broadcast` 唤醒全部线程，适用于"多个线程可以继续"或"各线程等待条件不同"的场景（如内存分配）。
- **状态变量不可省**：条件变量本身不存储状态，必须搭配共享变量（如 `done`、`count`）记录条件，否则会出现信号丢失或误唤醒。

## 六、总结

1. 条件变量实现"等待条件成立"的高效机制：条件不满足时线程休眠而非自旋，条件满足后通过信号唤醒；
2. 正确使用依赖三要素——锁保证原子性、状态变量记录条件、条件变量管理等待与唤醒；
3. 生产者/消费者问题是经典应用，标准解法是双条件变量配合 `while` 循环；
4. `signal` 精确但可能唤醒错误对象，`broadcast` 可靠但有额外开销；
5. 常见问题集中在三处：使用 `if` 而非 `while`、未持锁调用 `wait`、误以为条件变量会保存状态。

### 实验结果与回答

代码在 `OSTEP/homework/threads-cv/`，`make` 编译后运行。

### 1. 正确版 `main-two-cvs-while.c` 性能

**1 生产者 1 消费者，改缓冲区大小**（`-l 3000 -p 1 -c 1`，`-m` 取 1/2/10/100 均为 0.98~0.99s）。

为什么缓冲区大小没影响：只有 1 个生产者 + 1 个消费者，总共要做 3000 次 `put` + 3000 次 `get`，每次都要"加锁 → 放/取 → signal → 解锁"，这些操作次数是固定的。生产者放一个、消费者马上取走一个，缓冲区里始终只有 1 个数据，`-m` 开得再大也用不上。瓶颈是每次放取都要抢同一把锁，与缓冲区大小无关，所以时间不变：

```shell
./main-two-cvs-while -l 3000 -m 1 -p 1 -c 1 -t
```

```text
Total time: 0.99 seconds
```

**改生产者/消费者数量**（`-m 10 -l 2000`，1p1c 0.66s / 2p2c 1.31s / 4p4c 2.63s）。

为什么越加线程越慢：总项数 = 2000 × 生产者数，从 2000 → 4000 → 8000 翻倍，耗时也正好 0.66 → 1.31 → 2.63 翻倍。说明所有 `put`/`get` 都被同一把锁串行执行了，加线程**没有任何并行加速**，只是总工作量变多、时间线性增长：

```shell
./main-two-cvs-while -l 2000 -m 10 -p 4 -c 4 -t
```

```text
Total time: 2.63 seconds
```

**2 生产者 2 消费者，改缓冲区大小**（`-l 2000 -p 2 -c 2`，`-m 1` 为 2.22s，`-m 2/10/100` 均约 1.31s）。

为什么 `-m 1` 慢：缓冲只有 1 个槽，2 个生产者抢 1 个空位、2 个消费者抢 1 个数据，几乎每放一个/取一个都要阻塞一次、触发一次上下文切换。`-m ≥ 2` 后有至少 2 个槽，2 个生产/消费者基本能即时拿到空位或数据，阻塞次数骤降；再大也无用，因为同时活跃的线程就那么多：

```shell
./main-two-cvs-while -l 2000 -m 1 -p 2 -c 2 -t
```

```text
Total time: 2.22 seconds
```

### 2. 单 CV 版 `main-one-cv-while.c` 死锁

为什么死锁：单 CV 不区分"等空位"和"等数据"，生产者和消费者共享同一个 `cv`。`signal` 只唤醒**一个**等待者（且通常是最早排队那个）。当缓冲区空着时两个消费者先排队睡下，生产者放满后发 `fill` 唤醒一个消费者；生产者再进循环发现满了、自己睡下。此时消费者取走数据后发 `signal(empty)`，本应唤醒生产者，但队列里那个**更早排队的消费者比生产者靠前**，于是 `empty` 信号叫醒了这个消费者——它一看还是空、又睡回去，而生产者没人叫，全体睡死。

复现（`-l 2 -m 1 -p 1 -c 2` 跑了 30 次，第 27 次挂起；是竞态，概率低）：

```shell
timeout 2 ./main-one-cv-while -l 2 -m 1 -p 1 -c 2
```

```text
（挂起无输出，退出码 124 = 死锁）
```

错误唤醒轨迹（`-P 1 -C 0:0 -v`）：重点看 C0 的 `c5`（发 `signal(empty)`）之后，被叫醒的是 C1（`c3`）而不是生产者，C1 重查 `c2` 仍空又睡回去：

```shell
./main-one-cv-while -l 2 -m 1 -p 1 -c 2 -P 1 -C 0:0 -v
```

```text
  1 [*  0 ]    c3   <- C0 被 fill 唤醒
  0 [*--- ]    c4   <- C0 取走数据（count 1→0）
  0 [*--- ]    c5   <- C0 发 signal(empty)
  0 [*--- ]    c6   <- C0 解锁
  0 [*--- ]       c3  <- 被唤醒的是消费者 C1（错误！）
  0 [*--- ]       c2  <- C1 重查仍空，又睡回去
```

### 3. 单 CV 版 `main-two-cvs-if.c` 条件失效

为什么崩溃：`if` 只在睡觉前判断一次，醒来后直接往下走、不再检查缓冲区是否真的还有数据。多消费者下，A 被唤醒的瞬间 B 可能已经先把数据取走了，A 醒来直接 `do_get()` 就扑空，触发断言。对应正文"单条件变量 + `if`"那张跟踪表的最后一行"啊！没数据"：

```shell
./main-two-cvs-if -l 20 -m 1 -p 1 -c 2
```

```text
error: tried to get an empty buffer
```

### 4. extra-unlock 版 `main-two-cvs-while-extra-unlock.c` 竞态

为什么有竞态：`do_fill()`/`do_get()` 被挪到锁外，对 `buffer`/`fill_ptr`/`use_ptr`/`num_full` 的读写不再互斥。两个生产者可能同时通过 `while (num_full == max)` 检查（都看到"没满"），先后解锁，然后并发执行 `do_fill` 写同一个槽（要么 `fill non-empty` 断言失败、要么互相覆盖），`num_full++` 本身不是原子操作也会丢计数。

为什么复现不了：竞态窗口只有"解锁到 `do_fill` 之间"几条机器指令，两个线程恰好都卡在这个窗口里的概率极低，循环 100 次均未触发，但数据竞争客观存在：

```shell
./main-two-cvs-while-extra-unlock -l 30 -m 2 -p 2 -c 1
```

```text
（无输出，未触发断言——数据竞争存在，只是窗口极小）
```

### 5. 缓冲区大小对总时间的影响

**休眠在锁内**（`-P 0,0,0,0,1,0,0 -C 0,0,0,0,1,0,0`，`-l 4`），`-m` 取 1/2/4 均为 9.00s。

为什么是 9s 且不随 `-m` 变：生产者要产 4 项、每项在 `p4` 睡 1s = 4s；消费者要消费 5 项（4 个数据 + 1 个 EOS 结束标记）、每项在 `c4` 睡 1s = 5s。因为这两个 `sleep` 都在**锁内**，生产者睡的时候消费者拿不到锁只能干等，两端完全串行，总时间 = 4 + 5 = 9s；既然本来就串行，缓冲区再大也帮不上：

```shell
./main-two-cvs-while -l 4 -m 1 -p 1 -c 1 -P 0,0,0,0,1,0,0 -C 0,0,0,0,1,0,0 -t
```

```text
Total time: 9.00 seconds
```

**休眠在锁外**（`-P 1,0,0,0,0,0,0 -C 1,0,0,0,0,0,0`，`-l 4`），`-m` 取 1/2/4 均为 5.00s。

为什么变成 5s：`sleep` 挪到 `p0`/`c0`（加锁之前），生产者睡的时候不占锁，消费者可以同时消费，两者能重叠。总时间 = max(生产 4s, 消费 5s) = 5s（消费者是瓶颈）。`-m` 依旧没影响，因为 1 生产者 + 1 消费者下缓冲区从没填满过：

```shell
./main-two-cvs-while -l 4 -m 1 -p 1 -c 1 -P 1,0,0,0,0,0,0 -C 1,0,0,0,0,0,0 -t
```

```text
Total time: 5.00 seconds
```

综合结论：缓冲区大小只有在**多线程竞争**时才起作用（见第 1 点，2p2c 下 `-m 1` = 2.22s、`-m ≥ 2` = 1.31s）；1 生产者 1 消费者时不管休眠在锁内还是锁外都不受影响。原则是"够用即可"——缓冲区 ≥ 能同时活跃的线程数后，再增大无收益。
