# 26 - 基于事件的并发

除了线程，还有一种并发模型叫**事件驱动**：程序单线程跑一个"事件循环"，用非阻塞 I/O 主动监听事件（网络数据到了、文件 I/O 完了、信号来了），来一个处理一个。好处是不用锁、调度完全在自己手里；代价是要自己搞定异步 I/O 和状态管理，复杂度高。

## 一、事件循环

核心就一个无限循环，持续等事件、逐一分发：

```c
while (1) {
    events = 获取就绪事件（I/O、信号等）;
    for (每个事件 e) {
        调用事件处理器 event handler 处理 e;
    }
}
```

三个概念：

- **事件**：触发程序动作的来源——"网络数据到达""文件 I/O 完成""信号触发"；
- **事件处理器**：处理某类事件的代码片段。单线程下同一时刻只有一个处理器在跑，独占 CPU，天然没有并发冲突；
- **调度可控**：处理顺序由应用自己定，不靠 OS 线程调度——这正是事件驱动最大的吸引力。

前提是接口必须**非阻塞**：普通 `read()` 会阻塞整个程序、让事件循环停摆；非阻塞接口启动操作后立刻返回，后台完成再通过"事件"通知，循环才能一直转。

## 二、select()/poll()：怎么拿到就绪事件

"哪些 fd 可读/可写了"这件事，靠 `select()` 或 `poll()` 批量问 OS：

```c
int select(int nfds, fd_set *readfds, fd_set *writefds, fd_set *errorfds, struct timeval *timeout);
```

要点：

- `nfds`：要检查的最大 fd + 1（fd 从 0 开始）；
- `fd_set`：fd 集合，用 `FD_ZERO` 清空、`FD_SET` 添加、`FD_ISSET` 检查；
- `timeout`：NULL=无限阻塞，0=立即返回，非 NULL=指定超时；
- 返回值：就绪的 fd 总数。

典型用法：

```c
// 把 minFD~maxFD 都加进监听集合
fd_set readFDs;
FD_ZERO(&readFDs);
for (fd = minFD; fd < maxFD; fd++) {
    FD_SET(fd, &readFDs);
}
// 阻塞直到有 fd 就绪
int rc = select(maxFD + 1, &readFDs, NULL, NULL, NULL);
// 逐个处理就绪的 fd
for (fd = minFD; fd < maxFD; fd++) {
    if (FD_ISSET(fd, &readFDs)) {
        processFD(fd);
    }
}
```

`select()` 和 `poll()` 功能一样，都是水平触发的 I/O 多路复用；区别是 `select()` 受 fd 数量上限（默认 1024）限制，`poll()` 没有、接口更灵活。

## 三、为什么它没锁、调度可控

无锁的原因：单线程一次只处理一个事件，同一时刻没有第二个处理器碰共享数据，也就不需要锁——死锁、原子性违反、顺序违反这些线程并发 bug 全都凭空消失。

调度的好处：应用自己决定先处理谁——紧急信号、关键客户端可以插队；不用忍受 OS 线程调度的"次优"决策（频繁切换、资源竞争带来的性能损耗）。

## 四、难点

### 1. 阻塞系统调用 → 异步 I/O

事件循环是单线程的，处理器里一旦调了阻塞的 `open()`/`read()`（比如读磁盘），整个循环卡死，别的客户端全等。解法是用 OS 的**异步 I/O**：启动操作后立即返回，完成时通知。

- 核心结构 `struct aiocb`（AIO 控制块）：存文件 fd、偏移、缓冲区、长度；
- `aio_read(&aiocbp)` 启动异步读、立即返回；`aio_error(&aiocbp)` 查是否完成（0=完成，`EINPROGRESS`=没完成）；
- 通知方式：轮询 `aio_error()`（简单但低效），或 I/O 完成时 OS 发信号触发处理器（高效）。

### 2. 状态管理 → Continuation

线程模型里，函数调用的局部变量、返回地址都存在线程栈上，阻塞后恢复自动续上；事件驱动里异步 I/O 会把处理流程打断，状态得自己存，等 I/O 完成再接着干。

做法是 **Continuation**：把"没做完的逻辑 + 需要的状态"塞进一个结构体里。比如"读文件再写到 socket"——启动异步读时把 socket fd、文件 fd、缓冲区存进 continuation；读完成后，处理器拿文件 fd 查出这个 continuation，找到 socket fd 继续写。

### 3. 其余几个坑

- **多核**：单线程用不上多核；开多个事件循环（每 CPU 一个）就得同步共享数据，又回到锁的问题，无锁优势没了。
- **隐式阻塞**：就算没写阻塞调用，处理器执行时可能触发页错误，OS 会阻塞进程直到页加载完——这类隐式阻塞几乎躲不掉，会拉高延迟。
- **维护复杂度**：一个完整流程要拆成"启动 I/O""处理 I/O 完成"等多个处理器，代码连贯性差；而且一旦底层某接口从非阻塞变回归阻塞，事件循环会突然卡死，得一直盯着 API 语义。
- **I/O 接口不统一**：网络能走 `select()`，磁盘异步得用 `aio_*`，没有统一接口。

## 五、和线程模型对比

| 特性 | 事件驱动并发 | 线程并发 |
|------|--------------|----------|
| 调度控制 | 应用自主控制 | OS 调度，应用无控制权 |
| 同步需求 | 单线程无锁，多核需同步 | 需锁/条件变量同步 |
| 编程复杂度 | 高（异步 I/O + 状态管理） | 低（线性代码 + 栈保存状态） |
| 适用场景 | I/O 密集型（GUI、网络服务器） | CPU 密集 + I/O 密集 |
| 性能（无竞争） | 高（无线程切换开销） | 中（线程切换开销） |

## 六、总结

1. 事件驱动并发的核心是"事件循环 + 非阻塞 I/O + 异步处理"：优势无锁、调度可控，劣势复杂度高；
2. 三个关键技术：`select()`/`poll()` 监听事件、异步 I/O 避免阻塞、Continuation 管理状态；
3. 适用 I/O 密集、对调度要求严格的场景（node.js 服务器、GUI）；
4. 本质是放弃线程模型的简单，换对并发的完全控制——"控制力"与"复杂度"的取舍。

**5. 信号处理（SIGUSR1 清缓存）**

给服务器发 `SIGUSR1`，事件循环被打断后回来打印清缓存、继续服务：

```shell
kill -USR1 <pid>
```

```text

```

**4. 异步 I/O（aio-demo）**

`aio_read` 启动后立即返回，轮询 `aio_error` 直到完成：

```shell
./aio-demo /tmp/testfile.txt
```

```text
(reading asynchronously...)
read 24 bytes:
hello from file service
```

关键点：`select()` 被信号打断时返回 `EINTR`，代码里 `continue` 回到循环顶部继续，所以清完缓存还能接着服务，不会崩。

**6. 性能对比：事件驱动 vs 线程版（server-thread）**

用 `bench.py` 对两个服务器各发 2000 个 `TIME` 请求、50 并发：

```shell
gcc -o server-thread server-thread.c -Wall -pthread
./server-select 10092 &     # 事件驱动版
python3 bench.py 10092 2000 50
./server-thread 10093 &     # 线程版
python3 bench.py 10093 2000 50
```

```text
事件驱动 select 版: 2000/2000 requests in 0.13s = 14983 req/s
线程版:            2000/2000 requests in 0.14s = 14354 req/s
```

结论：`TIME` 这种几乎不干活的请求，两者吞吐差不多（事件驱动略快一点点，因为它省掉了每连接创建线程的开销）。差距要在请求变重时才拉开——线程版一个线程阻塞不影响别的线程，事件驱动版一旦在处理器里做了阻塞调用，整个循环就卡死，这也是任务 4 必须换成异步 I/O 的原因。
