# 6 - 进程比例份额调度

前面几章的调度器都在优化周转时间或响应时间，这一章换一个目标：**按比例**分配 CPU。即每个进程拿到的 CPU 时间，应该和它持有的"份额"成正比，谁份额大谁跑得多，而不是谁短谁先跑。这类算法在云服务器、虚拟机配额等"明确要按比例分资源"的场景很常用。

份额的具象表示叫 **Ticket（彩票）**：每个进程持若干张票，总票数是所有进程之和。进程 A 持 75 张、B 持 25 张，那么 A 就该拿到 75% 的 CPU。下面三种实现都围绕这个目标，差别在"随机还是确定、简单还是实用"。

## 一、彩票调度：随机抽奖

每次调度就抽一次奖：在 0~总票数之间生成一个随机数，这个数落在谁的票区间里，谁就赢下这个时间片。长期来看，每个进程赢的次数就逼近它的票数占比——概率正确，短期有波动。

彩票调度最妙的地方是"灵活调份额"的三板斧：

**彩票货币（ticket currency）**：用户用自己的内部"货币"给进程分票，操作系统再兑换成全局票。这样每个用户的总份额（全局票数）不变，内部想怎么分都行、互相不影响。用户 A、B 各有 100 张全局票，A 用内部货币 1000 分给两个工作、B 用内部货币 10 分给一个工作；兑换只改变他们内部的分配比例，不动对外占有的 100 张全局票：

```text
用户 A（100 全局票）                      用户 B（100 全局票）
  分给 A1、A2 两个工作                        只剩 B1 一个工作
  ├─ A1 = 500 内部币 ──兑换→ 50 全局票
  └─ A2 = 500 内部币 ──兑换→ 50 全局票         B1 = 10 内部币 ──兑换→ 100 全局票

兑换后全局票池 = 50 + 50 + 100 = 200 张，对这 200 张抽奖
```

**彩票转让（ticket transfer）**：进程可以临时把自己的票转给别的进程。客户端/服务端场景里，客户端把票转给服务端、让服务端优先更快地处理自己的请求，处理完再还回来：

```text
客户端 C ──① 转出彩票──→ 服务端 S    （S 拿到更多份额，更快处理 C 的请求）
客户端 C ←──② 归还彩票── 服务端 S
```

**彩票通胀（ticket inflation）**：进程可以临时提升或降低自己的票数。在互不信任的竞争环境里这招没用（贪婪进程会给自己狂加票、接管机器）；但在进程互信的环境里，进程直接给自己加票，就等于把"我要更多 CPU"的需求告诉了 OS，不用跟任何进程通信：

```text
进程 P（10 票）──通胀·自我加票──→ 进程 P（100 票）
  → 意思是：把"我要更多 CPU"的需求直接告诉 OS
  → 前提是进程互信；互不信任时会被贪婪进程滥用
```

**实现极简**：彩票调度最不可思议的其实是实现简单——只要一个好用的随机数生成器（用来抽中奖号）、一个记录所有进程的数据结构（一个链表）、以及所有彩票的总数。

具体做法：用链表存进程，每次调度分三步——在 `0 ~ 总票数` 之间随机生成中奖号 `winner`；从头遍历链表、用计数器 `counter` 累加每个进程的票数；累加结果第一次超过 `winner` 时，当前进程就是中奖者：

```c
int counter = 0;
int winner = getrandom(0, totaltickets);   // 0~总票数 里的一个随机中奖号
node_t *current = head;                    // 从链表头开始遍历
while (current) {
    counter = counter + current->tickets;  // 累加当前进程的票数
    if (counter > winner)
        break;                             // 第一次超过 winner，current 就是中奖者
    current = current->next;
}
// 此时 current 指向中奖者，调度它
```

比如 A=100、B=50、C=250，总票 400，抽中 300：先累加 A 的 100（counter=100，仍 <300 继续）、再加 B 的 50（counter=150，仍 <300 继续）、最后加 C 的 250（counter=400 >300，停下），所以 C 中奖。

一个优化：把链表按票数**从多到少排序**。这不影响正确性，但能让"票都攥在少数进程手里"时用最少次数就找到中奖者。代价是查找是 O(n) 线性遍历，但胜在无全局状态——加新进程只要往链表里加它的票，不用动别人。

优缺点：优点是简单、无全局状态、轻量；缺点是短期比例不准（20 次抽奖里，25% 份额的进程可能只跑 4 次甚至更少），进程运行时间越短，公平性越差。

## 二、步长调度：确定性的比例

彩票调度靠运气，步长调度把它换成确定性逻辑，保证每一步比例都精确：

1. **步长（Stride）**：与票数成反比，`Stride = 大常数 / 票数`，票越多步长越小；
2. **通行证（Pass）**：每个进程初始 Pass=0，每被选中运行一次就 `Pass += Stride`；
3. **调度规则**：每次选 Pass 最小的进程运行。

拿 A=100 票、B=50 票、C=250 票举例，取大常数 10000，步长 = 10000 ÷ 票数，于是 A、B、C 的步长分别是 100、200、40——**票越多、步长越小、被选中的次数越多**。

调度怎么走（初始三个 Pass 都为 0，每次选 Pass 最小的运行，跑完 `Pass += 自己的步长`）：

1. 三个 Pass 都是 0，任选 A 跑，A 的 Pass 变成 0+100=100；
2. 现在最小是 B（0），跑 B，Pass 变 200；
3. 最小是 C（0），跑 C，Pass 变 40（步长 40）；
4. 还是 C（40）最小，再跑，Pass 变 80；
5. 还是 C（80）最小，再跑，Pass 变 120；
6. 现在 A（100）最小，跑 A，Pass 变 200（追上 B）；
7. C（120）连续跑两次，Pass 变 160、200；
8. 三个 Pass 又都等于 200，回到起点，无限循环。

这段过程的 Pass 变化如下表：

| 步 | Pass(A) | Pass(B) | Pass(C) | 谁运行 | 运行后 |
|----|---------|---------|---------|--------|--------|
| 0 | 0 | 0 | 0 | A | A=100 |
| 1 | 100 | 0 | 0 | B | B=200 |
| 2 | 100 | 200 | 0 | C | C=40 |
| 3 | 100 | 200 | 40 | C | C=80 |
| 4 | 100 | 200 | 80 | C | C=120 |
| 5 | 100 | 200 | 120 | A | A=200 |
| 6 | 200 | 200 | 120 | C | C=160 |
| 7 | 200 | 200 | 160 | C | C=200 |
| 8 | 200 | 200 | 200 | 全部相等，重新循环 | |

数一遍：C 跑了 5 次、A 跑了 2 次、B 跑了 1 次，正好是 5:2:1，即 `250:100:50` 的票数比——比例精确、零随机波动。

优缺点：优点是比例精确、无随机波动；缺点是有全局状态（Pass），新进程进场时 Pass 初值不好设——设成 0 会让它瞬间霸占 CPU，需要额外处理，实现比彩票调度复杂。

## 三、Linux CFS：实用型的比例共享

CFS 是 Linux 的主调度器，思路是"谁占用 CPU 少，谁先跑"，用虚拟运行时（**vruntime**）来衡量每个进程已占用的 CPU 资源，每次挑 vruntime 最小的进程运行，从整体上逼近按权重（比例）分 CPU。

几个关键设计：

1. **动态时间片**：`sched_latency`（默认 48ms）是"一轮调度覆盖所有进程"的目标时长，`min_granularity`（默认 6ms）是时间片下限。时间片 = `sched_latency / 进程数`，若小于下限就取下限。4 个进程时时间片 12ms，10 个进程时理论 4.8ms、实际取 6ms。
2. **Nice 权重**：Nice 从 -20（最高）到 +19（最低），默认 0；每个 Nice 对应一个固定权重（Nice=0 是 1024，Nice=-5 是 3121）。一个进程的时间片占比 = 它的权重 / 所有进程权重之和。
3. **vruntime 累加**：`vruntime += (1024 / 权重) × 实际运行时间`——高权重进程 vruntime 涨得慢，于是能被选中更多次（分到更多 CPU）。
4. **红黑树**：把所有可运行进程按 vruntime 存进红黑树，插入/删除/查最小都是 O(log n)，千级进程也扛得住（链表是 O(n)）。
5. **睡眠唤醒**：长期睡眠的进程 vruntime 很低，醒来后会突然垄断 CPU。CFS 在唤醒时把它的 vruntime 设为红黑树里的最小值，避免这种饥饿。

**具体例子：权重怎么变成 3:1 的 CPU 比例**

进程 A（nice 0，权重 1024）和 B（nice 5，权重 335），`sched_latency = 48ms`：

| 进程 | nice | 权重 | 时间片（48ms 里） | vruntime 系数 | 一轮后 vruntime |
|------|------|------|-------------------|---------------|-----------------|
| A | 0 | 1024 | 1024/1359×48 ≈ 36ms | 1.00 | +36.0 |
| B | 5 | 335 | 335/1359×48 ≈ 12ms | 3.06 | +36.7 |

三步连起来看：时间片先按权重分（A 36ms、B 12ms，约 3:1）；跑完 vruntime 按系数累加——A 系数 1（跑 36ms → `+36`）、B 系数 `1024/335≈3.06`（跑 12ms → `+36.7`）；一轮后两者 vruntime 几乎持平，下一轮仍挑 vruntime 小的先跑，3:1 的比例就这样稳定维持。关键就是一句：**权重定时间片占比，vruntime 系数（1024/权重）把这个占比固定下来**，高权重进程时间片大、但 vruntime 涨得慢，所以总能排前面。

红黑树存的就是"所有可运行进程"，按 vruntime 从小到大排，最左节点 = vruntime 最小 = 下一个运行：

```text
红黑树（按 vruntime 排序，最左最小，O(log n) 查最小）
             [C: 40]
            /       \
        [A: 36]   [D: 55]
           \
          [B: 36.7]

当前 A 的 vruntime 最小、先跑；跑完 A 的 vruntime 变大，重新插回树里。
```

睡眠唤醒的坑：沉睡的进程不耗 CPU、vruntime 一直很低，一醒来按"vruntime 最小"会突然霸占 CPU；CFS 的做法是唤醒时直接把它的 vruntime 抬到红黑树当前最小值，让它正常参与竞争、而不是饿死别人：

```text
唤醒：A 睡了很久，vruntime 还是 2000（很小）
CFS 把 A 的 vruntime 改成 min(红黑树) ≈ 40，A 才能和别的进程公平竞争
```

## 四、三种算法对比

| 特性 | 彩票调度 | 步长调度 | CFS（Linux） |
|------|----------|----------|--------------|
| 比例保证 | 概率性（长期正确） | 确定性（短期也正确） | 近似比例（实用平衡） |
| 实现复杂度 | 极低 | 中等 | 较高（工业级） |
| 新增进程兼容性 | 极佳（无全局状态） | 较差（需处理 Pass 初值） | 极佳（红黑树动态插入） |
| 适用场景 | 简单比例分配、轻量系统 | 需精确比例的场景 | 通用操作系统 |
| 优先级支持 | 无（需扩展票数） | 无（需扩展步长） | 原生支持（Nice+权重） |

## 五、总结

1. 比例共享调度的核心是按份额分 CPU，Ticket 是份额的统一载体。
2. 彩票调度胜在简单灵活，步长调度胜在比例精确，CFS 胜在实用高效、能落地到 Linux。
3. CFS 靠动态时间片、红黑树、vruntime 这三板斧平衡了公平性、效率和扩展性。
4. 局限：对 I/O 密集进程不够友好（睡眠后可能拿不到公平份额）；"份额该给多少"（票数/权重怎么定）本身仍是个没有统一答案的问题。

## 六、作业方向（Simulation）

通过 `homework/cpu-sched-lottery/lottery.py` 模拟彩票调度。`-l 时长:票数,...` 指定作业（时长和票数），`-s` 指定种子，`-q` 指定时间片。核心任务：

1. 不同随机种子下，3 个进程的调度结果与比例匹配度；
2. 极端 Ticket 分配（1:100）对调度的影响（低 Ticket 进程是否能运行）；
3. 进程长度、时间片大小（`-q` 参数）对公平性的影响；
4. 绘制公平性随进程长度变化的图表，对比彩票调度与步长调度的差异。

### 1. 不同种子下 3 个进程的调度（seed 1）

```shell
./lottery.py -j 3 -s 1 -c
```

seed 1 随机给出 3 个进程：Job 0（长度 1、84 票）、Job 1（长度 7、25 票）、Job 2（长度 4、44 票），总票 153。每次抽奖就是"随机数 mod 总票数 ＝ 中奖票，落在谁的票区间里谁跑"：

```text
Random 651593 -> Winning ticket 119 (of 153) -> Run 2
Random 788724 -> Winning ticket 9   (of 153) -> Run 0
  --> JOB 0 DONE at time 2
Random 93859  -> Winning ticket 19  (of 69)  -> Run 1
Random 28347  -> Winning ticket 57  (of 69)  -> Run 2
  ...（省略中间若干次）
  --> JOB 2 DONE at time 6
  --> JOB 1 DONE at time 12
```

票区间按累计切分：Job 0 占 [0, 83]、Job 1 占 [84, 108]、Job 2 占 [109, 152]。中奖票 119 落在 Job 2 的区间、9 落在 Job 0 的区间，于是分别跑 Job 2、Job 0。

注意结果：票最多(84)、长度最短(1)的 Job 0 先完成；票最少(25)、长度最长(7)的 Job 1 最后(12)。彩票调度只看票数概率、不看长短，所以不会像 SJF 那样优先短作业——这点和上一章的 MLFQ 完全不同。

### 2. 极端票数分配（1:100）

```shell
./lottery.py -l 10:1,10:100 -s 0 -c
```

```text
Job 0 ( length = 10, tickets = 1 )
Job 1 ( length = 10, tickets = 100 )

Random ... Winning ticket 62 (of 101) -> Run 1
Random ... Winning ticket 51 (of 101) -> Run 1
 ...（连续 10 次全是 Run 1）
  --> JOB 1 DONE at time 10
Random ... Winning ticket 0  (of 1)   -> Run 0
 ...（之后每次都是 Run 0）
  --> JOB 0 DONE at time 20
```

Job 1 占 100/101 ≈ 99%，前 10 次抽奖全被它拿走、直接跑完；Job 0（1 票）一次都没轮到，直到 Job 1 退出、总票只剩 1，它才"必中"跑完。极端票差下低票进程不是永久饿死，而是"等高票进程跑完才轮得到"——事实上的临时饿死。

### 3. 等票长作业的公平性（大数定律）

```shell
./lottery.py -l 100:100,100:100 -s 0 -c
```

Job 0、Job 1 各 100 票、各要 100 个单位，共 200 次抽奖。统计全部 200 次：

```text
Run 0 恰好 100 次，Run 1 恰好 100 次
  --> JOB 0 DONE at time 192
  --> JOB 1 DONE at time 200
```

200 次抽样里 100:100 几乎完美，应了"长期均值 ＝ 票数占比"（大数定律）。对比任务 1 里总共才 12 次抽奖，比例明显飘。换几个种子完成时刻有 ±8~10 的波动（JOB0/JOB1 谁先完成在 190~200 之间跳），但跑的次数始终贴合票数比。结论：进程越长、抽奖次数越多，比例越准；越短越看运气。

### 4. 时间片大小（-q）对公平性的影响

```shell
./lottery.py -l 10:1,10:100 -q 10 -s 0 -c
```

```text
Random 844422 -> Winning ticket 62 (of 101) -> Run 1
  --> JOB 1 DONE at time 10
Random 757955 -> Winning ticket 0  (of 1)   -> Run 0
  --> JOB 0 DONE at time 20
```

`-q 10` 让"赢家一次跑满 10 个单位"，但**不改变抽中的概率**。Job 1（100 票）第一次就抽中、跑满 10 个单位即完成；Job 0（1 票）还是得等高票进程退出才能跑。把 `-q` 从 1 提到 10，低票进程并没有变公平——它照样被高票进程压着，时间片大小只决定"赢一次能干多久"。

整体趋势：彩票调度的公平性随进程长度增大而变好（偏差相对变小），而步长调度始终精确，差别在"随机 vs 确定"——这也是两者的本质区别。
